# Лапа рядом — план тестирования MVP

**Версия:** 0.1  
**Дата:** 21.10.2026  
**Статус:** спецификация тестов; выполнение ещё не начато  
**Приоритет:** P0 — обязателен для демонстрации, P1 — после выполнения P0  
**Предмет тестирования:** веб-приложение «Лапа рядом», исходная PostgreSQL, целевая Digital Q.DataBase, миграция данных и демонстрационный стенд.

> **Важно:** этот файл описывает тесты, критерии и ожидаемые результаты. Он не утверждает, что приложение создано, тесты запущены, Digital Q.DataBase установлена или миграция уже выполнена. Любые статусы `PASS` могут появиться только после реального исполнения с приложенными доказательствами.

## 1. Назначение и приоритет источников

Цель — сделать качество MVP воспроизводимым: разработчик или ИИ-агент получает входные данные, конкретные действия, ожидаемый результат и способ доказать его. Главные риски — неверные остатки, двойной учёт, обход прав приюта, утечка кодов и фиктивная «миграция» без фактического переноса данных.

При противоречии не изменять требования молча. Источники:

1. `01_PRODUCT_REQUIREMENTS.md` — требования `FR-001—033`, `VAL-01—10`, `NFR-01—11`, `DB-01—05`, бизнес-правила и `AC-01—08`.
2. `02_USER_FLOWS.md` — сценарии `UF-P*`, `UF-S*`, `UF-A*` и экранные состояния.
3. `03_DATA_MODEL.md` — схема, инварианты и тесты `DM-01—13`, порядок блокировок.
4. `04_TECHNICAL_ARCHITECTURE.md` — маршруты API, сессии, безопасность, миграция и `AT-01—12`.
5. `05_DEVELOPMENT_PLAN.md` — зависимости, задачи `QA-*`, `QDB-*`, `DEMO-*`, критерии выпуска.

Решения текущего документа **не изменяют** существующие правила: предложение действует 7 суток; после частичной передачи его нельзя подтверждать повторно; `fulfilled` и `closed` терминальны; единица измерения после создания не меняется; фактическое получение не равно обещанию.

## 2. Стратегия тестирования

| Уровень | Инструмент / среда | Что проверяем | Требуемый результат |
|---|---|---|---|
| Unit | Vitest, без БД, локальное время под контролем | валидация, преобразования, правила переходов, арифметика | Все P0-unit тесты проходят |
| API integration | Vitest + Fastify `inject` / HTTP + **реальный PostgreSQL** | схемы, SQL, ограничения, доступ, транзакции | Все P0-интеграционные тесты проходят |
| Concurrency | Несколько независимых соединений с реальной БД | гонки резервирования/приёмки, порядок блокировок | Ни один инвариант не нарушен |
| Browser E2E | Playwright + реальный API + реальная БД | пользовательские пути, ошибки, адаптивность | `AC-01—07` проходят |
| Migration | PostgreSQL → реальный Digital Q.DataBase | перенос именно существующих строк и сверка | Скрипт верификации возвращает `PASS` |
| Target DB regression | Те же тесты на Digital Q.DataBase | совместимость `pg`, SQL и транзакций | Критические тесты повторены и пройдены |
| Demo rehearsal | Зафиксированная сборка, демонстрационный браузер | живой сценарий Миланы, повторный запуск | Нет ручных исправлений в БД на сцене |

**Запрещено:** считать SQLite или mock `pg` заменой SQL-интеграционных проверок; заявлять `PASS` по результату статического ревью; заменять миграцию повторным seed на целевой СУБД; подменять живую демонстрацию видео без явной маркировки.

## 3. Тестовые окружения и подготовка

### 3.1. Изолированные контуры

- **TEST-PG:** временная PostgreSQL, созданная специально для тестов; отдельный пользователь с правами только в этой БД.
- **TEST-QDB:** отдельная тестовая Digital Q.DataBase с подтверждённой версией и доступом через `pg`. Пока доступа нет — тесты имеют статус `BLOCKED`, но не `PASS`.
- **DEMO-QDB:** отдельный неизменяемый до выступления набор данных на Digital Q.DataBase; тесты, удаляющие данные, здесь не запускаются.
- **WEB-E2E:** тестовый сервер фронтенда и API, подключённый к TEST-PG или TEST-QDB; внешние SMS, карты, платежи и AI-сервисы не требуются.

`reset-demo`, destructive-migrations, `TRUNCATE`, `DROP` разрешены **только** на выделенном тестовом/демонстрационном контуре с проверкой идентификатора целевой БД и явным подтверждением. Никогда не направлять их на неизвестную или общую БД.

### 3.2. Начальный набор данных

Seed должен быть воспроизводимым и помечен в UI «Демонстрационный проект. Приюты и заявки вымышлены».

| ID для тестов (алиас, не DB UUID) | Приют / объект | Начальное состояние |
|---|---|---|
| S-A | «Добрые лапы», Москва | опубликован, представитель `repA` |
| S-B | «Тёплый дом», Красногорск | опубликован, представитель `repB` |
| S-C | «Хвостатый друг», Химки | опубликован, представитель `repC` |
| S-H | «Тестовый скрытый приют» | неопубликован; создаётся в отдельном тесте |
| N-20 | Корм для собак, S-A, `pack` | `target=20`, `reserved=0`, `received=0`, `available=20` |
| N-2 | Отдельная потребность S-A | `target=2`, `reserved=0`, `received=0`, `available=2` |
| N-15 | Корм для кошек, S-B | `target=15`, `reserved=0`, `received=0`, `available=15` |
| N-CLOSED | Потребность S-A | `closed`, исторические записи сохранены |
| N-FULL | Потребность S-C | `fulfilled`, получено ровно столько, сколько требуется |

Основной пользовательский seed включает не менее трёх вымышленных приютов и 8–12 потребностей из документа 01. Дополнительные технические фикстуры (`N-2`, `N-CLOSED`, `N-FULL`, `S-H`) создаются в **изолированных тестах**, чтобы не ломать публичный демонабор.

Два аккаунта `repA` и `repB` обязательны для тестов разграничения прав, `admin` — для администрирования. Пароли/секреты задаются в тестовом окружении и не включаются в репозиторий или отчёты.

### 3.3. Требования к фикстурам

- Каждый тест получает независимые данные (новая БД/схема, откат тестовой транзакции или уникальные UUID). Нельзя полагаться на порядок тестов.
- Для тестов с конкурентными запросами использовать отдельные соединения и **не** оборачивать весь тест в одну внешнюю транзакцию, скрывающую изменения от других соединений.
- Для проверки срока управлять **временем, которое сравнивает сервер/БД**, а не только часами браузера. Допустимы изолированно созданные строки с контролируемым `expires_at` и фиксированные UTC-моменты.
- Каждая проверка значений должна читать реальные данные по API **и**, для интеграционных тестов, по SQL.
- Результаты, зависящие от часов, фиксировать относительно стабильного `t0`, явно записанного в тесте.

## 4. Формат тест-кейса и доказательств

Один тест содержит `ID`, приоритет, источник требования, окружение, предусловия, шаги, ожидаемые результаты и свидетельство. Разработчик записывает реальный исход как `PASS`, `FAIL`, `BLOCKED` или `NOT_RUN`.

- `PASS` — исполнен, каждый ожидаемый результат подтверждён.
- `FAIL` — исполнен, есть расхождение; создаётся дефект с условиями воспроизведения.
- `BLOCKED` — нет объективно необходимой зависимости (например, доступа к Digital Q.DataBase).
- `NOT_RUN` — тест не запускался.
- `SKIPPED_P1` — отложен с согласованным приоритетом P1, не входит в P0-выпуск.

Для каждого отчёта сохранять: Git commit SHA, Node.js, ОС, версию приложения, источник/цель БД, UTC-время, команды, количество тестов по статусам, `requestId` и **обезличенные** логи. Не сохранять секреты предложений, пароли, cookie, ключи идемпотентности, строки подключения с паролем.

## 6. API и SQL-интеграционные тесты (IT)

### 6.1. Публичные каталоги

**IT-01 — опубликованные приюты (P0; AT-01, FR-001—003).** Поднять seed с S-A, S-B, S-C и S-H. Запросить `GET /api/v1/shelters`. Ожидать три опубликованных приюта, отсутствие S-H; `GET /api/v1/shelters/{S-H}` должен дать нейтральный 404. В карточке S-A есть адрес, часы приёма и потребности. Проверить, что в ответах нет хешей и внутренних данных.

**IT-02 — потребности, фильтры и пагинация (P0; FR-005—010).** `GET /api/v1/needs` без параметров возвращает только публично допустимые записи; `search=корм`, `city=Москва`, `category=food` применяются корректно по отдельности и совместно. `pageSize=51` не должен обходить максимум `50`; невалидные параметры дают предсказуемую ошибку. Отдельная сортировка — P1. Проверить `GET /api/v1/needs/{id}` для опубликованной активной и скрытой потребности.

**IT-03 — четырёхпольный баланс (P0; FR-006—009).** Для N-20 проверить `target=20`, `reserved=0`, `received=0`, `available=20`; затем на тестовых записях отдельно создать действующие/истёкшие обещания и подтверждённые передачи. Ожидать, что баланс совпадает с агрегатным SQL и что `available >=0`. Не маскировать отрицательный баланс через `GREATEST(0, …)`.

### 6.2. Предложения и резервы

**IT-04 — создать анонимное предложение (P0; AT-02, AC-02).** Отправить `POST /api/v1/offers` с `needId=N-20`, `quantity=3`, новым UUID `idempotencyKey`. Ожидать `201`, код из 20 Base32-символов в группах по 5, `expiresAt≈createdAt+7d`; **код только в ответе**, в БД лишь `code_hash`. Баланс N-20 = **20 / 3 / 0 / 17**. Обновить страницу/выполнить новый GET: данные не исчезли.

**IT-05 — безопасный повтор (P0; AT-03, DM-11).** Отправить прежнее тело с тем же `idempotencyKey`. Ожидать `200`, тот же `offerId` и восстановленный тот же код; в `offers` ровно одна новая строка, резерв не удвоен.

**IT-06 — повтор с изменёнными параметрами (P0; DM-12).** Повторить `idempotencyKey` из IT-04, изменив `quantity` или `needId`. Ожидать `409 IDEMPOTENCY_CONFLICT`; строк и резервов не прибавилось. Повторить этот тест также для уже `received`/`expired` предложения: новый резерв не создаётся.

**IT-07 — превышение доступного и валидаторы (P0; VAL-01—02).** При остатке 17 запросить 18, 0, дробное, отрицательное, неверный UUID, слишком длинное тело. Ожидать `409 INSUFFICIENT_AVAILABLE_QUANTITY` или `400/422 VALIDATION_ERROR` соответственно. После каждого отказа таблица `offers` и баланс неизменны.

**IT-08 — невозможность резервирования закрытого/исполненного/скрытого (P0; FR-003, FR-009, BR-04).** Прямым API запросить резерв для `closed`, `fulfilled`, неопубликованного приюта, а также полностью обещанной активной потребности. Все запросы отклоняются, даже если фронтенд ошибочно показал кнопку. Данные не меняются.

**IT-09 — истечение (P0; AT-07, AC-05, DM-06—07).** При `t0`: цель=10, зарезервировано=3, свободно=7. Установить тестовое `expires_at=t0−1ms`, не запускать фонового задания. Новый GET должен сразу показать резерв=0, свободно=10 (эффективный статус `expired`), даже если физический `offers.status='reserved'`. Приёмка по коду запрещена; новая помощь на освободившееся количество разрешена. Тест не должен ждать реальные семь суток.

**IT-10 — отмена предложения (P0; FR-026).** Сотрудник S-A отменяет активное предложение 3 шт. Ожидать статус `cancelled`, резерв уменьшается на 3, `received` не меняется; повторная отмена даёт конфликт без нового изменения. Чужой сотрудник получит отказ.

### 6.3. Получение и корректировка потребностей

**IT-11 — полная приёмка (P0; AC-03).** При действующем резерве 3 сотрудник S-A вызывает `POST /api/v1/shelter/receive` с `receivedQty=3`. Ожидать одну строку `deliveries`, `offers.status='received'`, баланс **20 / 0 / 3 / 17**.

**IT-12 — частичная приёмка (P0; AT-05, AC-04, DM-04).** При чистой цели=20 зарезервировать 5, подтвердить `receivedQty=3`. Баланс из **20 / 5 / 0 / 15** становится **20 / 0 / 3 / 17**. Непереданные 2 освобождены. Статус предложения `received` окончателен; второй передачей по тому же коду нельзя добрать 2.

**IT-13 — повторное подтверждение (P0; AT-06, DM-02/05).** Повторить `POST /receive` по уже принятому коду, в том числе в двух почти одновременных запросах. Ожидать один `deliveries.offer_id`, один учёт фактически принятого количества, второй ответ `409 INVALID_STATE`. Дополнительный прямой SQL `INSERT deliveries` с тем же `offer_id` в *изолированном тесте* должен нарушить `UNIQUE`.

**IT-14 — некорректное количество при приёмке (P0; FR-024).** При резерве 5 проверить `receivedQty=0`, `-1`, `6`, `2.5`, строку. Все отклоняются до изменения БД; `receivedQty=1` разрешён.

**IT-15 — исполненная потребность (P0; требования §5).** При цели=3 зарезервировать и подтвердить 3. Ожидать `needs.status='fulfilled'`, баланс 3 / 0 / 3 / 0; новые предложения и редактирование запрещены.

**IT-16 — изменение цели (P0; AT-10, DM-08).** При `target=20`, `received=4`, активный резерв=5 попытаться задать цель `8` (отклонить), `9` (разрешить, свободно=0), `15` (разрешить, свободно=6). Смена единицы измерения после создания должна отклоняться. При `newTarget == received`, резерв=0, статус должен стать `fulfilled`.

**IT-17 — закрытие потребности (P0; DM-09, FR-027).** У активной потребности есть два действующих предложения и одно истёкшее. Представитель закрывает потребность. Ожидать `closed`, все **действующие** предложения отменены в той же транзакции; истёкший код не становится действующим; прежние deliveries сохранены. Новый резерв запрещён; при сбое транзакции не допускается «половинчатое» закрытие.

**IT-18 — создание и редактирование приюта администратором (P0; FR-029—030).** `admin` создаёт неопубликованный приют, задаёт адрес и часы, публикует, назначает `shelter_rep`; приют появляется публично только после публикации. Пароль сохраняется как Argon2id-хеш. Обычный представитель не может вызвать методы `admin`.

## 7. Аутентификация, права и безопасность (SEC)

| ID | Приоритет | Действие | Ожидаемый результат |
|---|---|---|---|
| SEC-01 | P0 | Вызвать защищённый маршрут без cookie / с отозванной / истёкшей сессией | `401`, изменения отсутствуют |
| SEC-02 | P0 | Войти `repA`, отправить `shelterId=S-B` в body и попытаться изменить N-15 | `403`/`404`, принадлежность определяется только по сессии |
| SEC-03 | P0 | `repA` вводит код предложения S-B и неизвестный код | Одинаково нейтральный отказ; наличие чужого кода не раскрывается |
| SEC-04 | P0 | `repA` пытается закрыть N-15, отменить предложение S-B | Отказ; баланс S-B не изменился |
| SEC-05 | P0 | Обычный посетитель обращается к admin/shelter POST/PATCH | `401`/`403` без мутаций |
| SEC-06 | P0 | Неверный пароль, повторный вход, logout | Нейтральная ошибка при неверном входе; logout отзывает сессию; старой cookie пользоваться нельзя |
| SEC-07 | P0 | Отключить аккаунт сотрудника после создания сессии | Следующий защищённый запрос запрещён |
| SEC-08 | P0 | Проверить cookie и защищённые маршруты | `HttpOnly`, `SameSite`; `Secure` при HTTPS; защита CSRF на небезопасных запросах |
| SEC-09 | P0 | Передать строку `' OR 1=1 --` в поиск/логин/поля | Не происходит обхода условий, SQL выполняется параметризованно |
| SEC-10 | P0 | Ввести HTML `<script>alert(1)</script>` в название/описание приюта | Строка безопасно отображается как текст, JS не выполняется |
| SEC-11 | P0 | Отправить много запросов создания предложений/логина/поиска кода | Срабатывает ограничение частоты с `429`, основная БД остаётся согласованной |
| SEC-12 | P0 | Инспектировать JSON, страницы, логи, миграционный отчёт | Нет `password_hash`, `code_hash`, cookie, секрета, raw кода или строки подключения с паролем |
| SEC-13 | P0 | Получить успешный ответ создания предложения | Заголовок `Cache-Control: no-store`; код не включён в URL и localStorage |
| SEC-14 | P0 | Отключить БД во время чтения/модификации | `503 DATABASE_UNAVAILABLE` или определённая серверная ошибка; нет ложного успешного результата и фрагментарной записи |
| SEC-15 | P0 | Запустить `reset-demo` не в demo/test-окружении | Отказ без очистки данных; нет публичного HTTP reset-эндпоинта |
| SEC-16 | P1 | Проверить клавиатурные формы, видимые фокусы, aria/label и контраст | Действия доступны без мыши, ошибки читаются |

**Проверка CSRF:** в режиме cookie-auth небезопасные методы должны требовать предусмотренную архитектурой проверку CSRF-токена и/или надёжный контроль `Origin`. Отсутствие ожидаемой защиты — дефект безопасности, даже если обычный сценарий UI проходит.

**Граница проверки:** эти тесты обеспечивают базовую безопасность демонстрационного MVP, а не сертификацию или разрешение на публикацию с настоящими приютами. Перед публичным запуском требуется отдельная оценка обработки технических метаданных и процедур подтверждения реальных приютов.

## 8. Конкурентность и целостность данных (CC)

Тесты выполняются на настоящей PostgreSQL с двумя или более независимыми подключениями и затем повторяются на Digital Q.DataBase. На каждом прогоне проверяются API-ответы, реальные таблицы и агрегаты. Таймауты и время блокировок фиксируются.

**CC-01 — последние 2 упаковки (P0; AT-08, AC-06).** Предусловие: `target=2`, нет резервов/доставок. Одновременно отправить два разных `POST /offers` с `quantity=2` и разными ключами. Ожидать **ровно один успешный** ответ и один корректный `409`, конечный баланс **2 / 2 / 0 / 0**, одна новая строка. Повторить серию ≥20 раз на новых изолированных фикстурах; число повторов — контроль надёжности теста, не свидетельство промышленной нагрузки.

**CC-02 — дробление на несколько заявок (P0).** При `target=10` одновременно отправить, например, 10 запросов по 3 единицы с разными ключами. Успешных суммарно не больше 10 единиц (при дискретном размере 3 — не больше трёх заявок); `available >=0`, нет ошибок FK/статусов.

**CC-03 — создание vs закрытие (P0).** В момент конкурентного `POST /offers` выполнить `/shelter/needs/:id/close`. Допустимы разные порядки коммитов: либо созданное предложение затем отменено закрытием, либо создание получило отказ. **Недопустимо:** `closed` с действующим резервом, созданным уже после закрытия.

**CC-04 — приёмка vs отмена/истечение (P0).** С одним резервом почти одновременно отправить `receive` и `cancel`. Только одна терминальная судьба; `deliveries` существует тогда и только тогда, когда подтверждение выиграло гонку. При истечении сравнение срока производится актуальным временем под блокировкой.

**CC-05 — два receive по одному коду (P0).** Оба запроса отправлены одновременно. Одна передача, один окончательный статус, никаких дополнительных количеств. Не допускается двойной `INSERT`, даже если API повторно вызывается после таймаута клиента.

**CC-06 — скрытие приюта vs резерв (P1).** Если реализован FR-033, `admin` одновременно скрывает приют, а посетитель предлагает помощь. После коммита скрытия новый резерв не должен проходить. Уже действующие резервы **не отменяются** только из-за скрытия.

**CC-07 — уменьшение цели vs резерв (P0).** Одновременно уменьшить `target=10` до 5 и запросить резерв 7. Успешна лишь согласованная последовательность; итог всегда `received+reserved <= target`. Не ожидать один строго определённый порядок победителя.

**CC-08 — отказ посередине транзакции (P0).** В тестовой версии service/repository намеренно вызвать исключение после первой SQL-мутации, но до `COMMIT` в операции receive/close. Ожидать полный `ROLLBACK`, исходные статусы/суммы без частичных изменений. Безопасный test-only fault injection недоступен извне и выключен в demo/production.

**Проверить порядок блокировок:** все операции с потребностью используют `shelters → needs → offers` и отдельный свежий `READ COMMITTED` снимок после блокировок, как в документе 03. Наличие случайной блокировки в противоположном порядке — дефект, даже если гонка не воспроизвелась.

## 10. Миграция PostgreSQL → Digital Q.DataBase (MIG)

Этот этап нельзя заменить успешно пройденными тестами на PostgreSQL. Каждый `MIG-*` исполняется на **реальном целевом экземпляре**. Зафиксировать фактическую версию/сборку продукта: простая строка `SELECT version()` не всегда достаточна для идентификации конкретной реализации.

### 10.1. Предварительная проверка совместимости

**MIG-01 (P0).** Подключиться через `pg`, выполнить `SELECT 1`, параметризованный запрос, `BEGIN/ROLLBACK`, проверку `UUID`, `BYTEA`, `TIMESTAMPTZ`, `CHECK`, `UNIQUE`, `FOREIGN KEY`, `SELECT … FOR UPDATE`. Создать и прочитать строку в безопасной временной таблице. **PASS** только если все нужные механизмы подтверждены; один `SELECT 1` недостаточен.

**MIG-02 (P0).** В пустой TEST-QDB применить `001_initial.sql`, `002_auth_sessions.sql` и действующие следующие миграции. Проверить таблицы, индексы, `need_balances`, `schema_migrations`. Повторный запуск мигратора не должен повреждать схему или дублировать изменения. Все отклонения от PostgreSQL документируются и перепроверяются на обоих контурах.

### 10.2. Контрольный набор для фактического переноса

**MIG-03 (P0).** В TEST-PG создать не только seed, но и реальную историю: несколько действующих/истёкших/отменённых/полученных предложений, одну частичную передачу, закрытую и fulfilled потребности, представителей приютов. Сохранить **необработанные наборы UUID и хешей** для локальной машинной сверки (не для публикации). Заблокировать запись на время экспорта, сделать резервную копию.

**MIG-04 (P0).** Убедиться, что целевые предметные таблицы пусты, и запустить `migrate-data.ts` **именно для копирования существующих строк** в порядке `shelters → accounts → needs → offers → deliveries` с сохранением идентификаторов, времён, статусов, байтовых значений. Не запускать повторно seed на цели. `auth_sessions` не переносятся, служебные миграции применяются обычным мигратором.

**MIG-05 (P0).** Смоделировать ошибку переноса на чистой TEST-QDB после вставки части строк. Проверить откат целевой транзакции без «половинчатых» переносов. Повтор разрешён только после проверки пустоты/безопасного сброса отдельной тестовой цели; никаких скрытых `TRUNCATE` общего сервера.

### 10.3. Сверка данных

**MIG-06 (P0).** Скрипт `verify-migration.ts` сравнивает все пять предметных таблиц:

| Показатель | Ожидаемое сравнение |
|---|---|
| `COUNT(*)` в каждой таблице | Точное совпадение |
| Множества `id` | Точное совпадение |
| FK между сущностями, `accepted_by` | Точное совпадение, нет сирот |
| Поля и значения каждой предметной строки | Точное совпадение по типам и смыслу, без округлений |
| `offers.code_hash` | Побайтовое совпадение |
| `idempotency_key` | Точное совпадение |
| `created_at`, `expires_at`, `received_at`, `cancelled_at` | Одни и те же моменты UTC |
| Распределение статусов | Совпадение, учитывая физические значения |
| Вычисленные balances на одном фиксированном `t_check` UTC | Совпадение по каждой потребности |
| `available_qty >= 0`, `received+reserved<=target` | Истинно на обеих БД |
| Дубли по `deliveries.offer_id` | Отсутствуют |

**Критический нюанс:** «активно обещано» зависит от текущего времени. Для сравнения вычисленных резервов использовать **один фиксированный** `t_check`, переданный в SQL как параметр в обе БД. Нельзя сравнивать два значения `now()` с интервалом, в котором резерв истекает.

**MIG-07 (P0).** Заведомо изменить в изолированной копии один `code_hash`, `received_qty` или FK, запустить verifier. Ожидать `FAIL` и ненулевой код выхода; verifier не должен «случайно» объявить миграцию успешной по одним только количествам строк. Это тест **тестирующего механизма**, не порча демонстрационной базы.

### 10.4. Переключение на целевую СУБД

**MIG-08 (P0).** Переключить только подключение `DATABASE_URL` на TEST-QDB, оставив `SERVER_OFFER_SECRET` неизменным. После запуска сотрудник входит заново; старые сессии не копировались. Проверить чтение ранее перенесённой истории, поиск по ранее созданному секретному коду в безопасном test-only сценарии и идемпотентный повтор с исходным ключом: прежний `offerId` восстанавливается, новый резерв не создаётся.

**MIG-09 (P0).** Повторить на Digital Q.DataBase **AT-02, AT-05—08, AT-11—12, все `AC-01—08`** и весь основной браузерный путь. Для `AC-08` доказательством служит не декларация, а реальный отчёт сверки и подтверждённая работа API на Digital Q.DataBase.

**MIG-10 (P0).** Сохранить `migration-report.md`: версии/сборки, способ подключения без паролей, состав перенесённых таблиц, числа строк, сверки и результаты регрессии, выявленные несовместимости и исправления. Приложить безопасные логи и короткий живой фрагмент демонстрации.

### 10.5. Остановка при ошибках миграции

Если несовместимы транзакции, `FOR UPDATE`, типы данных, `BYTEA`, ограничения или нельзя подтвердить перенос, выставить `BLOCKED`/`FAIL`, зафиксировать дефект и не ставить статус проекта `MIGRATED`. Наличие работающего приложения на PostgreSQL допускает только `SOURCE_READY`.

При отличии фактических имен скриптов обновить `README.md` и этот раздел, не имитируя их выполнение. Доступы, URI и секреты загружать из локальных переменных окружения; не печатать в вывод терминала.

Рекомендуемый порядок работы ИИ-агента: unit → API/SQL → SEC → CC → E2E на PostgreSQL → миграция → регрессия на Digital Q.DataBase → демопрогон. Раннюю проверку `MIG-01/02` провести **параллельно с разработкой**, как требует `05_DEVELOPMENT_PLAN.md`.

## 16. Критичность дефектов и правила остановки

| Критичность | Пример | Решение |
|---|---|---|
| **Blocker** | Отрицательный остаток, двойная приёмка, чужой доступ к данным, пароли/коды в логах, неподтверждённая миграция, работающая только исходная БД | Запрет статуса `DEMO_READY` |
| **High** | Нельзя пройти основной сценарий, ошибка частичной приёмки, нарушенные права, отсутствует обязательный P0-экран | Исправить до демо |
| **Medium** | Некритичная ошибка фильтра, текстовое несоответствие, неудобство на одном размере экрана | Исправить по возможности, если не мешает P0 |
| **Low** | Декоративная неточность, не влияющая на понимание/действие | Допустима в известном списке |

При любом P0 `FAIL` выпуск блокируется до исправления и регрессии. При недоступности Digital Q.DataBase статус `BLOCKED` не заменяется `PASS`; демонстрационный конкурсный критерий не выполнен, даже если исходная версия работает.

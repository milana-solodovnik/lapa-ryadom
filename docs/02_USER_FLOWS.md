# Лапа рядом — пользовательские сценарии и структура экранов

**Документ:** `02_USER_FLOWS.md`  
**Версия:** 0.1 (рабочая спецификация)  
**Дата:** 21 октября 2026 года  
**Основание:** `00_PROJECT_CONCEPT.md`, `01_PRODUCT_REQUIREMENTS.md`  
**Назначение:** основа проектирования интерфейса, клиентских маршрутов и сквозных тестов MVP  
**Статус:** готов к реализации P0; предварительные UX-решения отмечены отдельно

## 1. Принципы и границы

«Лапа рядом» — адаптивное русскоязычное веб-приложение для адресной помощи приютам для животных. Три роли: **посетитель без регистрации**, **представитель приюта с авторизацией** и **администратор**.

Главный пользовательский результат: человек находит актуальную потребность, указывает количество, получает секретный код; приют по этому коду подтверждает фактическое получение. В интерфейсе всегда различаются четыре величины: **требуется / активно обещано / получено / свободно для новых предложений**.

Приоритеты: **P0** — обязательный MVP; **P1** — улучшение при наличии времени; **P2** — вне текущего объёма. Сценарии ниже не расширяют функциональность, заданную `01_PRODUCT_REQUIREMENTS.md`; выбор маршрутов и подписей — предварительное UX-решение.

**Не делаем:** регистрацию добровольцев, чат, оплату, оформление доставки, карту с геопозиционированием, поиск животных, персональные профили помощников. В демоверсии используются только вымышленные приюты и потребности.

## 2. Карта приложения (information architecture)

### 2.1. Публичная зона

```text
/                         Главная: поиск потребностей и обзор приютов
/needs                    Каталог потребностей с фильтрами (P0)
/needs/:needId             Страница потребности и форма предложения (P0)
/shelters                  Каталог приютов (P0)
/shelters/:shelterId        Страница приюта, адрес/часы, потребности (P0)
/offer/result              Экран результата сразу после создания (P0)
/offer/status              Проверка статуса по секретному коду (P1)
/login                     Вход представителя/администратора (P0)
```

Главная (`/`) может отображать подборку актуальных потребностей и ссылки на оба каталога. **Она не является дополнительным обязательным P0-функциональным модулем**: допускается перенаправление с `/` на `/needs`.

### 2.2. Защищённая зона приюта

```text
/shelter                   Обзор потребностей своего приюта (P0)
/shelter/needs/new         Создание потребности (P0)
/shelter/needs/:id/edit    Редактирование активной потребности (P0)
/shelter/receive           Поиск предложения по коду, приёмка (P0)
/shelter/history           История подтверждений (P1)
```

### 2.3. Зона администратора

```text
/admin                     Список приютов с состоянием публикации (P0)
/admin/shelters/new        Создание приюта (P0)
/admin/shelters/:id        Изменение приюта, публикация/скрытие (P0/P1)
/admin/access              Назначение представителей и управление доступами (P0)
```

Указанные URL — **предлагаемые**, не фиксируют технологию роутинга. Можно объединить взаимосвязанные экраны в одной странице/панели, если все операции и состояния сохранятся. Прямые ссылки на публичные страницы должны открываться после перезагрузки.

### 2.4. Навигация

- Публичная шапка: логотип «Лапа рядом», **Потребности**, **Приюты**, **Вход для приютов**. Активный раздел визуально выделен.
- Кликабельное название приюта ведёт на его страницу; из потребности есть путь обратно к списку и к приюту.
- Внутри кабинета: **Мои потребности**, **Принять помощь**, **Выйти**; **История** добавляется при реализации P1.
- Администратору видны **Приюты**, **Доступы**, **Выйти**. Администратор не должен случайно попадать в контекст чужого приюта как обычный представитель.
- На всех публичных страницах демоверсии заметная, но не мешающая полоса: **«Демонстрационный проект. Приюты и заявки вымышлены»**.

## 3. Основные сценарии посетителя

### UF-P01 (P0). Найти потребность и выбрать приют

**Начало:** посетитель открывает `/needs`, `/shelters` либо главную.  
**Цель:** найти конкретную полезную вещь/продукт, который нужен приюту.  
**Предусловие:** есть опубликованные приюты и активные потребности.

1. Пользователь видит карточки потребностей или переходит к списку приютов.
2. В `/needs` вводит название вещи (например, «корм»), при необходимости выбирает категорию и населённый пункт.
3. Список обновляется; у каждой карточки видны приют, населённый пункт, категория, приоритет, единица измерения и четыре числа: требуется, обещано, получено, свободно.
4. Пользователь открывает потребность, читает описание, адрес передачи и часы приёма приюта.
5. Если свободно > 0 — видит действие **«Предложить помощь»**; если свободно = 0 — получает пояснение «Всё необходимое уже обещано или получено» и не может создать предложение.

**Результат:** посетитель выбрал актуальную потребность.  
**Альтернативы:** пустая выдача — «Ничего не найдено. Сбросьте фильтры» и действие **«Сбросить фильтры»**; у приюта нет открытых запросов — «Сейчас открытых запросов нет»; скрытый приют и его потребности не видны публично.

**Важно:** в каталоге потребностей фильтры по названию, категории и населённому пункту обязательны (FR-008). Отдельный фильтр *на странице каталога приютов* — P1 (FR-004). Не смешивать эти приоритеты.

### UF-P02 (P0). Предложить помощь и сохранить код

**Начало:** открыта активная потребность со свободным остатком > 0.  
**Цель:** зарезервировать реальное количество помощи, не предоставляя контакты.

1. В карточке или на странице потребности посетитель нажимает **«Предложить помощь»**.
2. Открывается встроенная форма (допустимо модальное окно): «Сколько вы можете передать?»; рядом указана единица измерения и максимальное текущее свободное количество.
3. Посетитель вводит целое число от 1 до доступного остатка и нажимает **«Подтвердить предложение»**.
4. На время запроса кнопка недоступна, показывается индикатор сохранения; повторные нажатия не должны создавать несколько резервирований. Сервер **повторно** проверяет допустимость числа и остаток в транзакции.
5. После **успешного ответа сервера** пользователь видит результат: **«Предложение принято»**, наименование, количество, приют, секретный код, срок действия предложения и адрес/часы передачи.
6. Пользователь копирует или записывает код. Объяснение: **«Сохраните код и покажите его при передаче вещей. Мы не сможем отправить его вам по почте или телефону»**.
7. В каталоге количество «обещано» увеличивается, свободный остаток уменьшается, но «получено» остаётся прежним.

**Результат:** предложение со статусом `reserved` записано в БД; код известен посетителю; резервирование действует 7 суток от момента создания.

**Ошибки и развилки:**

- Ноль, отрицательное, дробное или нечисловое количество — сообщение рядом с полем, запрос не отправляется.
- Остаток уменьшился после загрузки страницы — **«Это количество уже недоступно. Сейчас можно предложить: N ед.»**; обновить цифры, предложить изменить количество.
- Потребность закрыта, исполнена или приют скрыт до сохранения — запрет, обновлённый статус и ссылка к каталогу.
- Обрыв сети / 5xx — **«Не удалось подтвердить предложение. Проверьте соединение и попробуйте ещё раз»**. Не показывать код или «успех» без ответа сервера. Для безопасного повтора реализации нужен механизм защиты от повторов запросов (детали — `04_TECHNICAL_ARCHITECTURE.md`).

**Особенность кода:** секретный код не помещать в URL, аналитику и журналы. Экран результата можно сформировать из результата успешного запроса; при обновлении страницы код может исчезнуть, поэтому предупредить о необходимости сохранить его **до выхода**. Не обещать восстановление кода в MVP.

### UF-P03 (P1). Проверить статус своего предложения

**Начало:** пользователь открыл `/offer/status` и имеет сохранённый код.  
**Шаги:** вводит код → получает только статус `reserved` / `received` / `cancelled` / `expired`, количество и срок действия, без внутренних данных и без чужих предложений.  
**Ошибки:** неверный код — нейтральное «Предложение не найдено или код неверен»; защита от перебора обязательна, если эта функция реализована.  
**Результат:** пользователь понимает, действительно ли предложение ещё действует или передача подтверждена.

## 4. Сценарии представителя приюта

### UF-S01 (P0). Войти в кабинет

1. Представитель открывает `/login`, вводит учётные данные, нажимает **«Войти»**.
2. Сервер проверяет аутентификацию и роль; при успехе открывает `/shelter` **только своего** приюта.
3. В кабинете показано название приюта и его потребности.
4. Кнопка **«Выйти»** завершает сессию и возвращает к публичной зоне.

**Ошибки:** неверные данные — нейтральное «Не удалось войти. Проверьте логин и пароль» без уточнения, что именно неверно; истёкшая сессия — перенаправление на вход с безопасным сообщением; доступ к чужому объекту по прямому URL/API — отказ 403/404.

### UF-S02 (P0). Создать потребность

**Начало:** кабинет → **«Добавить потребность»**.

1. Открывается форма со следующими полями:
   - **Категория***: корм / наполнитель и гигиена / лежанки и текстиль / миски и инвентарь / переноски и амуниция / прочее;
   - **Название***: короткая строка, например «Сухой корм для собак»;
   - **Уточнение**: необязательный текст (марка/размер/особенности);
   - **Требуется***: целое число > 0;
   - **Единица***: шт. / уп. / кг;
   - **Приоритет**: обычный (по умолчанию) / срочный.
2. Представитель нажимает **«Опубликовать потребность»**.
3. Сервер проверяет поля и принадлежность приюта, создаёт `active`-потребность.
4. Пользователь возвращается в кабинет; карточка с первоначальными числами (`требуется=N`, `обещано=0`, `получено=0`, `свободно=N`) видна и публично, если приют опубликован.

**Ошибки:** обязательное поле не заполнено/количество некорректно — подсветить и объяснить; серверная ошибка — оставить заполненную форму и не заявлять об успехе.

### UF-S03 (P0). Изменить потребность

1. В кабинете нажать **«Изменить»** на активной потребности.
2. Изменить название, уточнение, категорию, приоритет или целевое количество.
3. При уменьшении цели сервер проверяет: новое значение **не меньше**, чем сумма уже полученного и действующих резервирований.
4. При корректном сохранении показывается **«Изменения сохранены»**, данные в публичном каталоге обновляются.

**Запрет:** при активных резервированиях и полученных передачах нельзя задним числом изменять единицу измерения. Это UX-уточнение во избежание неоднозначных количеств; если единица была выбрана ошибочно, администратор решает вопрос вне MVP. Закрытые и полностью исполненные потребности в MVP доступны для просмотра, но не для обычного редактирования; повторное открытие не предусмотрено. Это предварительное решение для согласования с `03_DATA_MODEL.md`.

**Ошибка:** новое целевое число ниже допустимого → **«Нельзя установить меньше N: часть помощи уже обещана или получена»**.

### UF-S04 (P0). Подтвердить передачу по коду

**Начало:** `/shelter/receive`; доброволец пришёл с вещами и кодом.

1. Представитель вводит код и нажимает **«Найти предложение»**.
2. Сервер проверяет секретный код, его принадлежность **текущему приюту**, актуальный статус и срок действия.
3. При успешной проверке показываются **потребность**, **обещанное количество**, **единица измерения**, **срок действия** и поле **«Фактически получили»**, по умолчанию равное обещанному количеству.
4. Представитель сверяет вещи и при необходимости указывает меньшее целое количество (от 1 до обещанного).
5. Нажимает **«Подтвердить получение»**. Перед финальным запросом отображается краткое подтверждение «Зачесть получение N ед.?» либо ясный итог на самой кнопке.
6. При успехе — **«Получение подтверждено: N ед.»**; предложение становится `received`, активное резервирование освобождается полностью, фактически полученное увеличивается **только на N**.
7. Интерфейс показывает обновлённые цифры и ссылку **«Принять следующую помощь»**.

**Пример:** обещали 5 уп., привезли 3 → `received += 3`, `reserved -= 5`, свободный остаток увеличится на 2 относительно состояния перед подтверждением.

**Ошибки:**

- Код неизвестен, не принадлежит этому приюту — нейтральное **«Действующее предложение по этому коду не найдено»**.
- Код уже использован, отменён или просрочен — получение **не** подтверждать; для собственного предложения можно показать безопасную причину («уже подтверждено», «отменено», «истекло»).
- Фактическое количество равно 0, больше обещанного или дробное — запрет сохранения.
- Два одновременных подтверждения — только одно изменяет данные; второе получает ответ о ранее выполненной операции.
- Нельзя менять «фактически получили» после финального подтверждения: повторные поставки по одному коду не поддерживаются.

### UF-S05 (P0). Отменить предложение или закрыть потребность

**Вариант А — отмена предложения:** представитель находит **активный** код своего приюта и выбирает **«Отменить предложение»** → видит подтверждающий вопрос → подтверждает → статус `cancelled`, резервирование освобождается. Полученное не меняется. Если код уже `received` или `expired`, отмена невозможна.

**Вариант Б — досрочное закрытие потребности:** в кабинете у активной потребности выбрать **«Закрыть потребность»** → если есть действующие обещания, обязательно предупредить **«Все активные предложения по этой потребности будут отменены. Связаться с добровольцами через сервис нельзя»** → подтвердить → потребность `closed`, новые предложения запрещены; связанные активные предложения отменяются атомарно.

**Автозавершение:** когда фактически полученное количество равно целевому, потребность автоматически переходит в `fulfilled`. Полностью обещанная, но ещё не полученная потребность **не** становится `fulfilled`.

### UF-S06 (P1). Посмотреть историю передач

Кабинет → **«История»** → список подтверждений: потребность, принятое количество и единица, дата/время. Данных добровольца нет. Нельзя открыть чужую историю. История — только просмотр.

## 5. Сценарии администратора

### UF-A01 (P0). Создать и опубликовать приют

1. Администратор входит и открывает `/admin`.
2. Нажимает **«Добавить приют»**; заполняет название, населённый пункт, краткое описание, адрес передачи помощи и часы приёма.
3. Сохраняет как неопубликованный либо публикует после проверки заполненности публичных полей.
4. Опубликованный приют появляется в каталоге; неопубликованный не доступен публично, а его потребности скрыты.
5. При изменении публичных данных каталоги показывают актуальную информацию.

**Ошибки:** отсутствуют обязательные публичные данные — публикация недоступна; неавторизованный доступ — отказ.

### UF-A02 (P0). Назначить представителя приюта

1. Администратор открывает **«Доступы»**.
2. Создаёт учётную запись либо выбирает существующую, назначает роль `shelter_manager` и **ровно один приют** (для MVP).
3. Устанавливает первичный секрет безопасным способом; пароль нельзя просмотреть после установки.
4. Представитель входит и видит только назначенный приют.
5. Администратор может отозвать доступ; последующие запросы отключённой учётной записи отклоняются.

**Уточнение:** самостоятельная регистрация приюта в MVP отсутствует. Механизм выпуска учётных данных и управления сессиями определяет `04_TECHNICAL_ARCHITECTURE.md`.

### UF-A03 (P1). Скрыть приют

В карточке опубликованного приюта выбрать **«Скрыть из каталога»** → подтвердить → приют и его потребности исчезают из публичной выдачи, данные и история не удаляются. Новые публичные предложения запрещены. Повторная публикация требует проверки текущих полей.

## 6. Экранный реестр и состояния

| ID | Экран | Главные элементы и действия | Обязательные состояния |
|---|---|---|---|
| UI-01 | Каталог потребностей `/needs` (P0) | Поиск, категория, населённый пункт; карточки и свободное количество | Загрузка, список, пусто, ошибка |
| UI-02 | Каталог приютов `/shelters` (P0) | Карточки приютов; переход к приюту | Загрузка, список, пусто, ошибка |
| UI-03 | Страница приюта `/shelters/:id` (P0) | Описание, адрес, часы, открытые потребности | Загрузка, открытые запросы, нет запросов, 404 |
| UI-04 | Потребность `/needs/:id` (P0) | Детали, четыре числа, количество, «Предложить помощь» | Доступно, всё обещано, исполнено/закрыто, 404, ошибка |
| UI-05 | Результат `/offer/result` (P0) | Код, количество, срок, адрес, предупреждение «сохраните код» | Успех только после серверного ответа; нет данных результата |
| UI-06 | Вход `/login` (P0) | Логин, пароль, «Войти» | Ожидание, неверные данные, ошибка сервера |
| UI-07 | Кабинет `/shelter` (P0) | Список собственных потребностей, создать/изменить/закрыть, приёмка | Список, пусто, ошибка, нет доступа |
| UI-08 | Форма потребности (P0) | Название, категория, описание, цель, единица, приоритет | Создание, редактирование, ошибки полей, сохранение |
| UI-09 | Приёмка `/shelter/receive` (P0) | Код, найденное предложение, количество фактической передачи, подтверждение, отмена | Не найдено, активно, просрочено, использовано, подтверждено |
| UI-10 | Список приютов администратора `/admin` (P0) | Карточки/таблица, создать, открыть, публикация | Список, пусто, отказ в доступе |
| UI-11 | Форма приюта и доступы (P0) | Публичные поля, состояние публикации, назначение представителей | Создание, изменение, валидация, успех, ошибка |
| UI-12 | Статус предложения (P1) | Ввод кода, статус, количество, срок | Нет кода, найдено, не найдено, ошибка |

**Заметка для реализации:** не дублировать публичные и административные формы без необходимости. Например, компонент карточки потребности можно повторно использовать в каталоге и кабинете, но права на изменение должны контролироваться сервером, не только видимостью кнопки.

## 7. Переходы и правила статусов

### 7.1. Предложение

```text
               создать при доступном остатке
                          │
                          ▼
                       reserved
                    /      │      \
       подтверждено    отменено    истекло
            ▼             ▼           ▼
         received      cancelled    expired
```

- `reserved` учитывается в «обещано», пока **не истёк срок** и запись не отменена/подтверждена.
- `received` отражает **фактически полученное**, даже если его меньше первоначально обещанного. Повторно подтвердить нельзя.
- `cancelled`/`expired` не уменьшают свободный остаток.
- Сервер считает истечение по времени UTC: даже если визуальный статус ещё не обновлён фоновым заданием, просроченный резерв уже не блокирует количество и не подтверждается.

### 7.2. Потребность

```text
active ─── подтверждено всё требуемое ──► fulfilled
   │
   └────── представитель закрыл ────────► closed
```

- «Всё обещано» — это **`active` с нулевым свободным остатком**, а не `fulfilled`.
- В `fulfilled` и `closed` нельзя создавать новые предложения.
- После перехода в терминальный статус пользовательская повторная активация не предусмотрена.
- При закрытии оставшиеся активные предложения отменяются в одной транзакции.

## 8. Унифицированные состояния интерфейса

| Состояние | Что делать |
|---|---|
| Загрузка | Показать индикатор; не отображать устаревшее число как гарантированное |
| Успех записи | Показать подтверждение **только после ответа сервера**, обновить связанный список/счётчики |
| Ошибка полей | Сообщение рядом с полем; не терять уже введённые данные |
| Конфликт остатков | Перечитать актуальные числа, показать сколько доступно сейчас |
| Нет данных | Понятное сообщение и релевантное действие (очистить фильтры, добавить потребность) |
| Ошибка соединения | Нейтральное сообщение и доступное повторение; без ложного результата |
| Нет прав | Не показывать закрытые данные; 401/403 на сервере и переход к входу/странице отказа |
| Просроченная сессия | Предложить войти снова; не выполнять незаметно защищённое изменение |
| Код истёк | Запретить приёмку, пояснить необходимость нового предложения |

**Не обещать рассылки:** без контактных данных добровольца сервис не уведомляет его о закрытии, отмене или истечении предложения. На экране результата честно объяснять, что код нужно сохранить и перед визитом желательно проверить актуальность запроса в каталоге.

| Контекст | Текст |
|---|---|
| Карточка потребности | **Предложить помощь** |

## 10. Адаптивность и доступность

- **Телефон от 360 px:** одноколоночные карточки, фильтры без горизонтальной прокрутки страницы, крупные нажимаемые действия. В кабинете приюта таблица допускает замену карточками; все функции доступны без наведения мыши.
- **Десктоп:** каталог в несколько колонок при достаточной ширине, фильтры в боковой панели или над списком, кабинет — список/таблица с понятными действиями.
- **Формы:** подписи полей вне плейсхолдеров, видимые ошибки, правильный цифровой ввод для количества, понятные состояния `disabled`.
- **Клавиатура:** логичный порядок Tab, видимый фокус, закрытие модальных окон через Escape, возврат фокуса на кнопку, открывшую окно.
- **Статусы:** не опираться только на цвет; рядом с количеством писать словами «обещано», «получено», «свободно».
- **Часы приёма и сроки:** хранить время истечения на сервере в UTC, отображать пользователю понятную локальную дату/время с указанием часового пояса, если он влияет на интерпретацию.

## 11. Порядок демонстрации (2–3 минуты)

**Подготовка:** загружены вымышленные данные, доступны аккаунт представителя приюта и два браузерных окна/профиля (публичный посетитель и кабинет). Приложение реально подключено к Digital Q.DataBase после проверенной миграции.

1. **10–20 сек.** Милана открывает каталог, показывает приют «Добрые лапы» и потребность «Сухой корм для собак — 20 уп.».
2. **20–30 сек.** В роли представителя приюта создаёт новую потребность **либо** показывает заранее созданную. Для короткого показа можно выбрать один путь.
3. **20–30 сек.** В роли посетителя предлагает 3 уп. и получает код. Счётчики: **20 требуется / 3 обещано / 0 получено / 17 свободно**.
4. **30–40 сек.** В кабинете вводит код, подтверждает 3 уп. Итог: **20 / 0 / 3 / 17**.
5. **20–30 сек.** Обновляет каталог, показывает, что состояние сохранилось после перезагрузки. Кратко говорит о связях данных, транзакциях и проверенной миграции на Digital Q.DataBase.

**Резервный вариант:** сохранить видеозапись того же реального сценария на случай проблем с сетью. Видео — страховка, не подмена реализации.
